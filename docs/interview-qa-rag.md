## 开场 30 秒（电梯稿）

> 这个项目把 18 篇真实券商研报建成了分析师的问答工作台：MinerU 统一解析成 Markdown，层级父子切块，子块进 Milvus 做稠密+BM25 双路召回、RRF 融合、BGE 重排加断崖截断，父块存 PostgreSQL 还原完整上下文；上层用 LangGraph 做 Agentic RAG——查询改写分解、元数据自动路由、反思循环。最大的收获是我没有"感觉式调优"：先用脚本从真实块反推构建了唯一命中约束的 gold 评测集，跑出 L0–L5 分层基线，用配对 Bootstrap 的 A/B 框架定位到瓶颈在**一阶段召回**而不是重排——重排把已召回证据的 top-5 转化率做到 89%，但证据进 top-20 候选只有 31%。这段经历让我把 RAG 从"跑通"做到了"可度量、可归因"。

## 一、业务场景与价值

### Q1 这个项目到底解决什么问题？业务价值怎么量化？

**考察点**：能否用业务语言而非技术语言描述价值；对"价值量化"的诚实度。

**参考回答**：金融分析师的核心痛点是**跨报告查资料和整合数据耗时**——一份结论要人工翻多篇研报核对原文。我做的系统让分析师用自然语言提问，直接拿到带出处的答案：每条结论标注 `[N]` 引用、报告日期、页码，可以一键跳回原文页图。价值量化上我们很克制：立项时写过"查资料 30 分钟 → 5 分钟"，但那是估值不是实测，所以验收口径**没有**用它，改用四项可自动计算的硬指标（hit_rate@5、evidence_rank≤3 占比、引用可溯源率、负样本拒答正确率）。我认为这是加分项——业务价值指标不掺水，验收全部落在可复现的自动指标上。

**追问预警**：那"30 分钟→5 分钟"后来验证了吗？→ 答：没有计时校准，因为真实用户试用环节由实施方扮演分析师（内部工具阶段），我们把它降级为方向性目标；如果给我更多时间，我会加一道埋点：每次问答记录"从提问到点击原文页"的时长和会话数，用行为数据替代估值。

### Q2 用户是谁？验收口径为什么只有自动指标？

**考察点**：需求边界意识；对"验收=指标"背后取舍的理解。

**参考回答**：用户是**单个分析师的工作台**（单用户 JWT，不做多租户——明确写进了非目标）。验收只看自动指标，是因为内部工具阶段没有真实用户试用，人工评估的主观性和成本都高；我们选择了可重复、可回归的机器口径。代价我也清楚：引用可溯源率这类指标只能证明"答案带可核查的出处"，不能证明"分析师觉得有用"，所以文档里把用户试用列为后续必须补的环节。

### Q3 原定场景是"跨券商对比同一指标"，为什么改成了"跨报告整合同一主题"？

**考察点**：需求变更的处理方式；是否理解"场景必须被语料支撑"。

**参考回答**：这是我在实测语料后发现并推动的需求变更。约定语料是 50–100 篇，实际只到位 **18 篇 / 318 页**（约 7 篇个股 + 5 篇行业 + 5 篇宏观周报 + 1 篇文本层乱码），而且**没有任何一只股票被 ≥2 篇报告覆盖**——"同一指标的多家券商口径"这个对照物在语料上构造不出来。我把证据链摆给需求方（逐篇标的清单），由需求方确认改场景为"跨报告整合同一主题"：多篇宏观周报对同一指标的表述、个股报告与行业报告对同一产业链的交叉印证，并强制多跳题证据来自 ≥2 篇不同文档。同时向需求方明确告知**代价**：原场景最有价值的"同一指标横向拉平"这次无法验证，且我们不做口径归一化，输出的仍是各报告原文口径 + 出处 + 日期。

**追问预警**：为什么不补充语料？→ 语料由需求方提供，到位 18 篇是硬现实；我的处理是把它写进风险表：小语料下全库检索更容易命中，hit_rate@5 天然偏乐观，**语料扩充后基线必须复测，不能外推**。

### Q4 为什么不做跨券商口径归一化、不做评级/目标价抽取？

**考察点**：需求裁剪的判断力（这是设计文档里的显式决策）。

**参考回答**：三个原因。① **错误率**：研报首页评级格式不统一，`2026E/FY26`、`归母净利/净利`、`亿/百万` 的换算一旦抽错，输出的是看似精确的错误数字，比"查不到"更危险；② **非必需**：目标场景是"查资料"，分析师要的是原文口径 + 出处 + 报告日期，换算本来就是他们的专业动作，我们不越俎代庖；③ **范围控制**：资源有限时优先打通"多格式解析 → 检索 → 溯源"主链路，归一化是明确的非目标，写进了 spec 避免范围蔓延。

### Q5 分析师凭什么敢用 AI 给的答案？如何避免幻觉？

**考察点**：幻觉治理是否是**全链路分层**的（而不是只在 prompt 里写"不要编造"）；误拒与幻觉的权衡意识。

**参考回答**：我的观点是幻觉无法根除，工程目标应该定为"**可检测、可溯源、可拒答**"——宁可拒答，不错答。具体做了五道防线，按链路顺序：

① **数据侧：知识源先干净**。入库时正则清洗页码/版权/导航噪声；段落级 SimHash 去重，文档间 SimHash 海明距离 ≤3 直接拦截——重复或矛盾的语料是幻觉的温床；页码归属匹配不上记 0 不猜，保证溯源信息本身不说谎。

② **检索侧：不给低质上下文**。断崖检测把重排分数断崖后的低分块截掉（保底 3 条），避免噪声稀释生成；再加一道"检索不足"守卫——所有来源的 rerank 分都低于 0.3 时直接判检索失败，走拒答而不是硬答。

③ **生成侧：约束生成行为**。温度压到 0.1 降低随机性；prompt 强制每条结论标注来源编号和报告日期；上下文有预算控制（文本块 2000 字符、表格 8000），避免长上下文被截断后拼贴出断章取义的结论。

④ **输出侧：自动审计 + 人工兜底**。`CitationValidator` 对每个 `[N]` 引用，取标记前后 100 字符的答案片段与来源前 500 字符算嵌入余弦相似度（≥0.4 通过），得分 <0.5 拒答、<0.8 标"低置信"提示用户；前端页码按钮弹出 `pymupdf` 渲染的原文页 PNG，"3 步内跳回原文"——分析师抽查一条引用只要几秒，这是敢用的核心。

⑤ **评测侧：把"防幻觉"当成可回归的指标**。评测集里专门放了负样本（前提错误/超范围问题，期望拒答而非编造），基线负样本拒答正确率 2/2；自动推断的过滤条件做成可见可改的 chip，低置信元数据打 needs_review 供人工修正。

**主动交代权衡**：防幻觉不是免费的——基线上有一道跨报告正例被拒答策略误拒（8 条来源 rerank 全低于 0.3），这直接拉低了引用可溯源率。误拒率和幻觉率是一对跷跷板，我的结论是两者必须在同一张 A/B 里联合调参、扩样后一起定阈值，不能为了一个好看的拒答率单边压误拒。

### Q6 语料才 18 篇，这个系统还有意义吗？扩到千份级要改什么？

**考察点**：对系统规模边界的清醒认知（报告局限一节原话级素材）。

**参考回答**：18 篇的价值是把**链路和评测协议**建扎实，而不是证明最终指标。我自己在报告里写了局限：小语料全库检索偏容易，hit_rate@5 偏乐观；证据只有 29 条、正例 18 题，层间差异不具统计显著性。扩到 500–5000 篇要动的地方我都排过：① 稠密侧口径（基线索引是 bge-small-zh 512 维——report.txt G3 已把它记为"模型与设计不符"；09-30 起已切到 bge-m3 1024 维并重灌索引，**但基线还没在 m3 索引上复测**；子块预算已按实测 token 密度对齐嵌入窗口（上限 256 token = 358 字符，实测 0% 超窗、稠密覆盖 100%；改前是 12.2% 超窗 / 84.7% 覆盖），但**索引还没按新切块重灌**、gold 证据 id 要重建）；② 重排候选集要封顶——CPU 上跑 cross-encoder 的成本随语料线性涨，千份级必须限定 rerank top-N；③ 元数据过滤必须真正接入 Agentic 链路（目前标准链路有、LangGraph 的 retrieve 节点没传 filters，这是我明确的 TODO）；④ 基线全量复测，确认指标不随体量劣化。

## 二、技术选型背后的思考

### Q7 解析层为什么选 MinerU？和直接用 PyMuPDF 抽文本比贵在哪？

**考察点**：是否真理解解析层在金融文档上的难点。

**参考回答**：研报的难点不是"抽出文本"，而是**保结构**：多栏版式、跨页表格、图片里的图表、扫描件。MinerU 是本地部署的版式解析模型（我们 pin 3.4.5），输出 Markdown + `content_list.json`，我主要用它的三点：① 版式还原成带标题层级的 Markdown，为后续"标题栈切父块"提供结构；② 表格识别——实测发现研报财务表是 **HTML `<table>` 而非 Markdown 竖线表**，识别不出来就进不了 PostgreSQL 整表链路；③ 内置 OCR——18 篇里有一篇文本层乱码，靠它走 OCR 救回来。PyMuPDF 我们也在用，但只做两件它擅长的事：抽嵌入图片和渲染原文页 PNG，解析主体交给 MinerU。代价是速度，实测约 **0.16 页/秒**，318 页跑了约半小时，所以入库流水线把它放在独立线程池限流。

### Q8 为什么子块进 Milvus、父块存 PostgreSQL，而不是全放一个库？

**考察点**：父子块架构的本质理解（简历核心卖点）。

**参考回答**：因为两者的访问模式完全不同。子块是"**检索粒度**"：要小、要进向量索引、要标量过滤；父块是"**上下文粒度**"：一篇 2000–3000 字符的完整章节，放进向量库既稀释检索密度，也浪费——它根本不需要被"搜到"，只需要被"按 id 取回"。所以：Milvus 只存子块 + 稠密/稀疏向量 + 标量字段；父块全文存 PostgreSQL `parent_chunks`（复合主键 collection+id），检索命中子块后按 `parent_id` 批量取回父块替换内容，并做 seen_parents 去重——同一父块下多个子块命中只还原一次。另外父块大小有约束：**只有 50–3000 字符的父块才替换**，避免把上下文撑爆；这个约束后来引出了一个重要 bug（见 Q22 表格 3000 陷阱）。

**追问预警**：为什么父块不用 Milvus 的 dynamic field 存？→ `enable_dynamic_field=False`，且大文本放向量库标量列会拖累 mmap 和 fetch；PG 的 JSONB/Text + SQLAlchemy 是更自然的文档存取层，还顺手获得了事务性 upsert。

### Q9 嵌入模型为什么选 BGE + ONNX INT8？这里有没有坑？

**考察点**：成本/合规权衡 + 诚实度（这是 G3 差距项，主动讲是加分）。

**参考回答**：选本地 BGE 有三个理由：① 数据合规——研报文本不出内网（只有检索片段会发给外部 LLM API，图片外发走审计日志）；② 成本与延迟——本地 CPU 推理，无按次计费；③ 中文效果稳定。工程上用 optimum 导出 ONNX 后 `quantize_dynamic` 做 INT8 动态量化，CPU 上延迟和内存都降一档。**坑我主动交代**：设计文档定的是 bge-large-zh，基线（09-28）实际跑的是 `BAAI/bge-small-zh-v1.5`（512 维）——report.txt G3 就是这条"模型与设计不符"的记录；09-30 我已换成 **bge-m3（1024 维、CLS pooling、ONNX INT8、CPU 推理）并重灌索引**，但**基线数字还没在新索引上复测**，所以下面这套指标仍然只代表 bge-small 时期的系统，这是我最想主动说清的版本状态。另有独立于模型的口径缺口——`onnx_embedder` 硬截断 512 token，而子块上限原来是 512×4 = 2048 字符（≈1370 token），**12.2% 的子块尾部没进稠密向量、只有 BM25 能看到**，这也是基线里"一阶段召回弱"的候选原因之一。两条的修复账都算过：重建集合 + 全量重嵌入成本可控——换模型这条已经做完（待复测）；压块这条代码也改完了（换算系数 ×4 → ×1.4，上限压到 256 token = 358 字符，实测 0% 超窗），**但索引还停在旧切块上**，重灌 + 重建 gold 证据 id 排在基线复测之后。

### Q10 BM25 稀疏路为什么用 Milvus 的 BM25 Function，而不是自己实现或上 Elasticsearch？

**考察点**：对稀疏检索实现方式的认知（简历写"BM25"，面试官常问自研还是现成）。

**参考回答**：用 Milvus 2.5+ 的 `Function(FunctionType.BM25)`：入库时从 content 字段自动生成 sparse_vector，查询时稀疏路直接传原始 query 文本，Milvus 自动做 BM25 编码。不自写的理由：分词、词频统计、倒排维护都是成熟功能，自研只会引入 bug 面；不上 Elasticsearch 的理由：那会多一套存储和一条数据同步链路，我们的过滤条件（`security_code ==`、行业 in 等）在 Milvus 标量过滤里就能表达，没必要为 BM25 单独引一套系统。**踩过的坑**：BM25 Function 需要 Milvus 2.5+，compose 里 pin 的还是 v2.4.0，实测检索报错后把服务端升到 v2.6.17；另外 pymilvus 的 `hybrid_search` 过滤表达式必须放在**每个 AnnSearchRequest 的 expr** 上，放顶层参数会被静默忽略——这是读文档+实测才确认的行为。

**追问预警**：效果上 BM25 帮了多少？→ 诚实回答：在 18 篇研报基线上，L0/L1/L2 三层的聚合指标逐位相同（都是 0.1389），但**逐题 top-5 有 7/18 题不同**，这是 n=18 的样本巧合，不能据此说 BM25 无效；反例是查询"153.62亿"这种数字型关键词，纯稠密前 5 完全不含证据块，混合检索把它排到第 1。在 28 题旧迁移集上混合+重排把 Recall@5 从 0.68 提到 0.91。

### Q11 双路分数怎么融合？为什么用 RRF 而不是加权求和？

**考察点**：RRF 原理与 k=60 的含义。

**参考回答**：用 pymilvus 的 `hybrid_search` + `RRFRanker(k=60)`。不用加权求和的核心原因：**两路分数量纲不可比**——稠密是 COSINE 相似度，BM25 是无上界的词频分数，归一化方案（min-max、z-score）都对新文档分布敏感且需要调参。RRF 只用排名：每条结果贡献 `1/(k+rank)`，k=60 意味着排名靠前的结果之间差距被平滑、排名靠后也有基础贡献，对两路都稳健，且没有任何要调的超参。工程细节：检索有过采样——重排开启时 `fetch_k = max(k, rerank_top_n×3)`，每路取 `limit = fetch_k×3`，给重排留足够候选；融合分数最后按最大值归一化到 0–1 方便前端展示。去重不在 RRF 层做，而在两处：父块还原按 parent_id 去重、merge_docs 按内容前 200 字符去重。

### Q12 重排为什么选 bge-reranker-v2-m3？为什么只取 top 3？

**考察点**：cross-encoder vs bi-encoder 的本质；延迟预算意识。

**参考回答**：bi-encoder（检索）是 query 和 doc 各自独立编码，快但交互浅；cross-encoder（重排）把 `[query, doc]` 拼一起过模型，能捕捉细粒度交互，精度高但每对都要跑一次前向，所以只能用在少量候选上。这就是"过采样 3 倍 → RRF → 重排取 top-N"漏斗的原因。具体实现：sentence-transformers 的 CrossEncoder 加载 `BAAI/bge-reranker-v2-m3`，本地 CPU，类级单例 + 推理锁（模型不是线程安全的，且要避免并发重复加载约 2GB 权重），query-doc 对截断到 2000 字符，默认 top_n=3。**它是整条链路里唯一被数据证明有效的环节**：28 题迁移集上重排开关让 MRR 从 0.58 到 0.91（配对 Bootstrap +0.3256，CI [0.20, 0.46]，判 pass）；18 篇研报基线上把已召回候选的 top-5 转化率做到 89%。代价是 CPU 延迟随候选数线性涨，语料到千份级必须限定重排候选集。

### Q13 "断崖检测"是什么？为什么需要它？

**考察点**：简历卖点，必须讲清算法和边界。

**参考回答**：解决"重排前送多少条候选进 BGE"的问题。候选按粗排分数降序后扫描相邻两条，满足**任一**约束即判定断崖（取最早一处截断）：① **绝对差距** `score[i]-score[i+1] >= 0.8`；② **相对跌幅** `(score[i]-score[i+1]) / score[i] >= 0.40`；③ **兜底**：即使命中，也至少保留 `min_topk = 5` 条（`RERANKER_CLIFF_MIN_TOP_K`，实际取 `max(min_topk, rerank_top_n)`，因此客户端把精排调到 10 时也不会因断崖拿不到 10 条），避免误判把上下文砍空。规则级禁用=该阈值设 0，两条都设 0 则整体禁用。要强调的是它**只截断、不扩召回也不降级**——它管理"给 LLM 多少上下文"，不管理"召回够不够"。基线里 cliff_on_off 的 A/B 判了 inconclusive（CI 跨 0），所以我从不说它带来了大幅提升，它的价值更多是防御性的：避免低分块稀释生成质量。

**必须主动交代的分数尺度事实**（面试官常追问的点）：绝对规则在数学上被相对规则**完全蕴含**——分数 ≤1 时 `gap >= 0.8` 必然推出 `gap/score[i] >= 0.8 > 0.40`；而 RRF 融合分的上界只有约 `2/61 ≈ 0.033`（`1/(60+rank)` 两路求和），0.8 在这种模式下**永不可达**。所以真正生效的是相对跌幅规则；保留绝对规则是为了显式表达"绝对断层"的意图，并让它在未来分数尺度 >1（换融合方式/换模型）时具备独立意义。它的代价是零（同一趟 O(n) 扫描内多一次比较），收益是意图可读。

### Q14 为什么要引入 Agentic RAG？它到底解决了什么问题？

**考察点**：是否对着**真实失败模式**讲动机，而不是"因为它火"；对代价和证据强度的诚实。

**参考回答**：标准 RAG 是"单发开环"系统——一个问题、检索一次、直接生成，检索好坏没有质检。它在我们的业务场景里暴露了三个真实失败模式，Agentic 层就是逐个对着它们设计的：

① **跨文档整合题一查就漏**。baseline 场景就是"跨报告整合同一主题的数据"，gold 集 20 题里 10 题是跨文档多跳。一次查询的 top-5 很难同时命中分散在多篇报告里的证据（多跳下 hit_rate 会饱和性虚高，这是我们在指标口径里明确写过的坑）。解法：rewrite 节点把问题拆成改写查询 + 3 个子查询 + 3–5 个关键词，retrieve 节点对每个子查询分别检索、跨知识库合并去重（merge_docs），把"一次命中率"变成"多次命中率"。

② **用户问得模糊**。分析师不会说"002056 2026 中报的燃机订单预期"，会说"那个订单超预期的票后来怎么样了"——实体缺失、口语指代，直接拿去检索必偏。解法：查询改写补全实体与术语（LLM 失败回退规则关键词）；元数据自动路由从问题推断 security_code/行业/报告类型等结构化过滤（白名单 + 申万词表硬校验、高置信才施加、前端 chip 可见可改），让"查某只票"走精确过滤而不是全库语义。我们后来专门加了 10 道**模糊问法题**（去掉券商名/简称/报告期）来度量这类场景。

③ **差检索直接进生成，没人刹车**。开环系统检索失败时，LLM 只能硬编或答非所问。解法：reflect 节点做"质检-返工"——top 文档平均 rerank_score ≥ 0.3 直接放行（跳过 LLM 调用省成本）；否则轻量模型（qwen-turbo）回 `SUFFICIENT` 或 `INSUFFICIENT:<新查询>`，用新查询重检索，最多 2 轮。

**代价和证据强度我也直说**：它不免费——改写和反思每轮都是额外 LLM 调用，延迟和成本都涨；子查询变多会引入噪声（早期 n=5 的 A/B 里 Agentic 臂 context_precision +14.1%，但 faithfulness 掉了 10%，样本太小不下结论）；跨文档至今仍是最难的部分（interview30 上 cross_doc 层 R@5 只有 0.2333，低于模糊层 0.40）；另外元数据过滤目前只接在标准链路，LangGraph 的 retrieve 节点还没传 filters——记录在案的待修项。我的总结：Agentic RAG 解决的是**查询表达与检索系统之间的语义鸿沟**（改写/分解/路由）和**开环无质检**（反思循环）两个问题；但它只放大已有召回的能力——我们的基线恰恰证明召回才是第一瓶颈，Agent 变不出没检到的东西。

**追问预警**：那为什么用 LangGraph，手写循环不行吗？→ 可行，本质就是带环状态图。选 LangGraph 是要它三样现成的东西：状态模型（AgentState TypedDict）、条件边一等支持（reflect → retrieve/generate）、astream 按节点产出事件（前端"改写中/检索中/重排中/生成中"直接映射节点名）。这是框架选型问题，不是架构必需，面试别把它说成"非 LangGraph 不可"。

### Q15 评测为什么用 Ragas + 自建证据指标双轨，而不是只跑 Ragas？

**考察点**：对 LLM-as-judge 局限的认知（README 里有现成的"指标口径与坑"）。

**参考回答**：因为 Ragas 这类文本级指标有**饱和问题**，我们在实践中踩实了两条：① `context_recall` 的 LLM judge 对 top-5 上下文普遍给 1.0，区分度接近零；② 自动生成的多跳题证据不可信时，`multi_hop_hit=0` 不能归因于检索。所以我建了**基于 chunk id 精确匹配的客观指标层**：Recall@5 / Precision@5 / MRR 按"检索返回的 chunk id 与标注证据 id 字符串相等"计算，另有 evidence_rank（证据块排名，未命中记 k+1）、parent_restore_rate（父块还原率）、文档级 hit_rate@5 / MRR@5 / NDCG@5 / doc_coverage。Ragas 侧保留**四指标**：检索链路的 context_precision（噪音）/ context_recall（盲区）+ 生成链路的 faithfulness（幻觉）/ answer_relevancy（跑偏）。早先还跑过 answer_correctness 与 context_entity_recall，后来下线了——四指标之外的口径会让同一份报告读两个标准，而且这两项与四项高度共线。两条腿的分工：chunk-id 层回答"检索系统准不准"，Ragas 回答"生成有没有辜负上下文"。报告里还做了防呆：未标注证据的条目指标记 n/a 不计入均值，**不会伪装成 0 分**；自动生成集里疑似坏标注的条目单列 suspect_annotations 清单。

### Q16 讲一下层级父块切分的完整流程和参数

**考察点**：简历第一卖点，参数必须脱口而出。

**参考回答**：入口是 `HierarchicalChunker`，流程五步：① 规则清洗（页码/版权/导航噪声正则）+ 段落级 SimHash 去重；② `_inject_heading_structure`：对没有 Markdown 标题的中文文档，按"第 X 编/章/节/条"、中文序号等 13 类编号标记注入标题层级（## 到 ######，行 ≤80 字符），很多研报转出的 Markdown 标题是丢的，这一步决定父块质量；③ `_split_into_parents`：用一个标题栈扫描，遇到一级标题入栈、出栈时结算父块——**父块 = 完整章节**，带 heading 和 heading_path（这是检索时能显示"所属章节"的原因）；④ 父块内部切子块：`RecursiveCharacterTextSplitter` 等价实现，子块 `chunk_size = 256×1.4 = 358` 字符、重叠 `25×1.4 = 35` 字符，分隔符中文标点优先；⑤ 建立父子关系：parent_id = sha256(source:parent:序号:heading:content)（序号防同一文档重复块撞主键），child_id = sha256(parent_id:content_hash)——**内容不变则 id 不变，天然幂等**，增量入库靠它。id 和 chunk_key 保留在检索结果里，评测侧据此做证据块对齐。

**参数怎么定的（含实测值）**：一句话——**父块没有长度参数（结构驱动），子块只有"上限 + 重叠"两个数**，实际粒度由版式结构决定，上限只在长段落上生效。
① 父块：切分由标题栈决定（= 完整章节），无标题文档按自然段切，长度不参与决策。v1 曾有一个 `PARENT_MAX_TOKENS=2000` 的父块上限，v2 起不再按长度拆分父块（章节腰斩会让引用变残），该参数与配置项**已删除**；父块长度兜底只存在于检索侧——`_expand_to_parents` 只在父块 ∈ [50, 3000] 字符时才替换子块内容。
② 子块：`DOCLING_CHUNK_MAX_TOKENS(256) × 1.4 = 358` 字符上限、`CHILD_OVERLAP_TOKENS(25) × 1.4 = 35` 字符重叠。`1.4` 是字符/token 换算系数，按实测密度反推（均值 1 token ≈ 1.5 字符，数字/英文密集块最坏 0.707 token/字符），这样配置项名字里的 token 数才真的等于块内 token 上限。**上限必须明显小于嵌入窗口**：太大等于没在管粒度（512 token 上限时只有 23% 的父块被切开，且块尾会被 512 窗口静默截断），太小则退化成碎片（128 token 时 99% 的子块 <200 字符）。
③ 这两个数怎么定的：上限取 **256 token ≈ 358 字符**（约 1~2 个自然段，中文 RAG 的常用粒度；配置名的 token 口径来自 Docling HybridChunker 的遗产），重叠 25 token ≈ 10%（LangChain 默认 4000/200 是 5%）。**没做过块大小的质量扫描**——我只做过"上限该落在哪"的粒度扫描；做过 A/B 的是检索层（k / rerank / HyDE / LangGraph）。
④ 实测（18 篇真实 MinerU markdown 重跑生产切块器，1080 text + 98 table）：text 子块 p50=207、p90=335、p95=346、max=357 字符（**上限确实在起作用：39% 的父块被切成多块**，而不是像 512 token 上限时只有 23%）；父块 597 个（不受修改影响），p50=215、p90=1216、max=11440 字符，其中 22.8% <50 字符（标题型）、3.7% >3000 字符 → **检索侧父块还原覆盖率 73.5%**。
⑤ 用真实分词器（`BAAI/bge-m3`）量的口径：**改前** 512×4 = 2048 字符 ≈ 1370 token，超过 embedder 的 512 窗口，**12.2% 的 text 子块尾部进不了稠密向量**、整体只有 84.7% 字符进稠密（15.3% 只有 BM25 能看到）；**现在** 子块 token p50=132、p90=215、p95=229、**max=263，0% 超窗、稠密覆盖 100%**，代价是 text 子块 654 → 1080（+65%，每个块更小所以总量没变）。overlap 35 字符 ≈ 块长的 10%。碎片率 47.6%。（注：基线索引是 bge-small-zh，中文约 1 字 ≈ 1 token，旧上限 2048 字符 ≈ 2000 token，那时截断比 bge-m3 更严重——这是"一阶段召回弱"的候选原因之一。）

**追问预警**：
- 为什么按字符不按 token？→ 纯标准库实现（避免 chunker 引 tokenizer，见 Q20 冷启动）；配置项只留 `DOCLING_CHUNK_MAX_TOKENS` / `CHILD_OVERLAP_TOKENS`（名字里的 token 含义由代码 `×1.4` 折算成字符，遗留的 `CHUNK_TOKENIZER` 已删除）。
- 那你怎么知道上限该取多少？→ 分两件事：**"上限会不会形同虚设 / 会不会退化成碎片"我扫过**——在真实语料上把上限从 128 扫到 512 token：128 token 时 99% 的子块 <200 字符（碎片化），512 token 时只有 23% 的父块被切开（等于没在管粒度），取中间拐点 256 token（39% 的父块被切开、token p90=215），另有回归测试锁住"不超过嵌入窗口"。**但"256 是不是检索最优"没验证过**——没做块大小的 A/B。方案：固定其它层，扫 `DOCLING_CHUNK_MAX_TOKENS ∈ {128,256,512,768}` × overlap 10%，用 gold20 跑 L0/L3 分层 + 配对 Bootstrap，主指标 R@5/MRR、护栏 parent_restore_rate，同时看 context_precision 是否随块变大而下降。代价是重建 gold 证据 id + 全量重嵌入，属"扩语料时一起做"。
- 父块为什么不设上限？→ 结构完整性优先（章节腰斩会让引用变残），长度风险改由检索侧 3000 字符门控兜底；代价是那 3.7% 的超长父块拿不到完整章节、只能给子块。
- 48% 的子块 <200 字符会不会太碎？→ 会：块太小则 BM25 词频信号弱、稠密语义稀。缓解靠父块还原把 50–3000 字符的父块拼回上下文，但这只是缓解不是解决。
- 表格/公式是原子块，不参与跨块切分。

### Q17 表格这条链路具体怎么做的？"3000 陷阱"是什么？

**考察点**：最有含金量的 war story，讲清"发现→机制→修复"。

**参考回答**：表格三段式：入库时 `_extract_atomic_units` 把 Markdown 竖线表和 **HTML `<table>`** 提为独占原子块；向量库里只存"**表头 + 首行**"摘要作索引（`block_type="table"`）；**整表**转 Markdown + 二维数组（JSONB）存 PostgreSQL 的 `table_chunks` 表。为什么这样设计：盈利预测表整表几千字符，整块嵌入既稀释向量又必然被截断，而"表头+首行"恰好是"这张表是什么"的最小语义单元，检索命中后再取整表。**3000 陷阱**：父块还原逻辑只在父块长度 ∈ [50, 3000] 字符时才替换子块内容，超过 3000 就**静默保留子块**——而表格子块的 parent_id 指向整表，整表几乎必然超 3000，如果表格走普通父块还原路径，整套"整表方案"会被静默退化成"表头+首行"，而且没有任何报错。我是在设计评审时推演出来的，修复是给表格建独立展开路径 `_expand_tables`：不受 PARENT_MAX_CHARS 约束，单表注入上限 8000 字符，超限**按行截断**并在 sources 标 `truncated: true`、答案里提示"表已截断，可点击查看完整表"——绝不静默删数据。同时 `_expand_to_parents` 跳过 table/image 类块，避免无效查询。有单测锁住这个行为（`test_retrieval_tables.py`）。

### Q18 图片多模态检索是怎么落地的？

**考察点**：简历"多模态检索"的实质内容；合规意识。

**参考回答**：① 抽取：pymupdf 按 `page.get_images` 抽嵌入图片，**按内容 md5 去重**——页眉 logo、水印每页都出现，不去重会重复付视觉模型的钱；key 用 `{页码}-{页内序号}`，和分析师看到的页码一致。② 存储：完整图入对象存储 `images/{文档名}/{页-序}.png`。③ 描述：DashScope qwen-vl-max 生成中文 caption，小于 5000 字节或 80px 的图直接跳过，失败重试 2 次，超过每文档 10 张只建占位；caption **作为独立 image chunk 入向量索引**（block_type="image"），这样"订单结构图"这类查询能靠文本语义命中图片。④ 降级：caption 失败的图仍入索引，内容是"[图片] 第 N 页"占位，不阻断入库。⑤ 合规：研报图片属敏感内容，**每次成功外发视觉模型都写一条 `image_egress` 审计日志**（挂 utils/audit.py）。

### Q19 页码溯源怎么实现的？有什么坑？

**考察点**：工程精度意识（页码是"3 步跳回原文"的基础）。

**参考回答**：MinerU 的 `content_list.json` 里每个内容块带 `page_idx`，切块时对每个子块用正文前缀去内容块里做最长前缀匹配，命中则取页码；跨页块用 40 字符探针扩展。三个实测踩到的坑：① 产物文件名**带文档名前缀**，按精确名找 content_list 永远找不到，会静默退化成无页码——改成通配 `*content_list.json` 匹配；② 匹配不上时页码记 **0，绝不乱填**——页码是溯源信息，错的比缺的更糟，最终归属率 906/1078 = 84.0%（旧切块口径；10-01 重灌后块数实测 1504，归属率待重测），缺的主要是表格/图表块；③ 渲染侧 `GET /api/documents/{source}/page/{page}`：先把原始 PDF 从存储 download 到本地临时文件（兼容 OSS 后端）再 pymupdf 渲染 PNG，DPI 144（72 读研报太糊），越界 404、非 PDF 400，临时文件即用即删。

### Q20 元数据抽取链路：正则、LLM、词表校验怎么配合？为什么校验这么严？

**考察点**：对"静默漏召"的深刻理解（设计文档原话级素材）。

**参考回答**：抽取字段：security_code/security_name/industry_l1/l2/report_type（个股|行业|宏观）/broker。链路是**正则优先 → LLM 补空缺 → 词表硬校验**：文件名规范（"名称(600519)-券商-日期"），正则命中率很高，LLM 只补正则抽不到的字段，一次结构化调用。校验三条硬规则：security_code 必须匹配 `^\d{6}$`；industry 必须落在**申万 2021 词表**（31 个一级 / 134 个二级，存 `assets/taxonomy/sw_industry.json`）且二级必须属于所选一级，非法值直接丢弃并置 needs_review；每条记录记 `meta_source`（regex/llm/manual）便于审计。**为什么这么严**：检索过滤是精确匹配（==/in），LLM 自由输出"白酒"，而库里是 `industry_l1 == "食品饮料"`，这条过滤会**静默漏召**——文档在库里，但被过滤条件挡住了，比查不到更难排查。配套两个兜底：空值**不参与过滤**（不会误收窄召回）；元数据自动过滤只在**高置信**时施加，抽不到或不唯一就宁可不加。实测还抓过一个全量性 bug：LLM 返回的 AIMessage 没解包就存库，导致**每篇**元数据都是空的——加了单测锁定。

**追问预警**：为什么 security_code 是单值字段？→ 行业研报覆盖 N 只股票没有合法单值代码，约定：个股研报填代码+行业，行业研报代码留空靠 industry 召回，宏观只填 report_type。查多只股票时 `security_code in [...]` 支持多值，但**问题里出现多只不同股票时整条丢弃代码过滤**——只过滤其中一只会让其它股票静默消失。

### Q21 入库流水线为什么是"线程池 + 进程池 + 线程池 + async"四种执行体混搭？

**考察点**：GIL/IO 模型理解，README 里有现成论证表。

**参考回答**：四个阶段的工作负载不同，执行体各选其最：① **解析**用 ThreadPoolExecutor + 限流（MINERU_MAX_CONCURRENCY）——MinerU 加载 GB 级 ONNX/GPU 权重，进程池化会让内存成倍涨，多进程毫无收益；② **切块**用 ProcessPoolExecutor（spawn）——规则清洗、SimHash、标题注入、层级切分全是**纯 Python CPU 密集**，受 GIL 限制，21 万字符文档实测进程池约 3.4s；③ **嵌入**用专用 ThreadPoolExecutor——ONNX runtime 是 C 层实现，推理期间释放 GIL，线程池足够，且 ONNX 会话本身串行化推理；④ **写库**在事件循环里 await——Milvus 是网络 IO。阶段间用有界队列衔接（INGEST_QUEUE_MAXSIZE），文档级流水线并行：一个文档切完块就能进嵌入队列，不等同批其它文档解析完。

### Q22 背压和失败隔离怎么做的？队列满了会发生什么？

**考察点**：生产化思维（README 关键行为一节）。

**参考回答**：① **背压**：各阶段队列有界，队列满时不再启动新解析，上传接口直接返回 **503**（不阻塞调用方），内存上界约为 MAXSIZE × MAX_UPLOAD_SIZE_MB——这是显式拒绝而不是 OOM。客户端应退避重试，重试安全是因为入库有**内容指纹幂等**：已入队的文件重传会命中指纹被增量跳过。② **失败隔离**：任一阶段异常只让该文件失败（task 置 failed + 中文原因），整批继续。③ **自愈**：阶段 worker 异常不终止、自动重启，supervisor 兜底；重启次数有 Prometheus 指标 `worker_restarts_total`，>0 说明发生过自愈。④ **可观测**：`ingest_queue_depth{stage}` 看瓶颈段（持续上涨的那段就是慢的）、`stage_seconds` 直方图看单文档耗时、`queue_rejected_total` 看背压触发次数。⑤ **降级**：进程池不可用（受限容器禁止 spawn）自动降级内联切块；短文档低于 INGEST_CHUNK_MIN_CHARS 直接内联。

### Q23 写入的原子性和并发安全怎么保证？

**考察点**：两阶段写库 + 锁设计（README 有专段）。

**参考回答**：核心是**两阶段 + 锁内最小化**：存储上传等网络 IO 放在锁外的 prepare 阶段，锁内只做"删旧行 + 插新行"的原子区（含文档间 SimHash 去重的"先查再插"），这样锁的持有时间最短，且支持多消费者在锁外并行做 IO。锁落在**资源侧**：KnowledgeBase 按 collection 自持写锁，入库流水线、对象存储事件回调、删除/管理路径共用同一串行点——不依赖各调用方自觉加锁，这是从"调用方加锁"演进来的，因为总有调用方忘记。单文档删除/覆盖走 remove(source)，支持按版本删。

### Q24 增量入库和版本管理怎么做的？

**考察点**：增量检测的两级设计 + 一个真实事故。

**参考回答**：两级检测。**文件级**：FingerprintStore 按 source 记 sha256 + mtime + size + simhash，JSON 原子写（tmp + os.replace + 线程锁）；哈希一致直接跳过解析和嵌入。**块级**：每块存 content_hash，diff_chunks 对比新旧 manifest 得到 unchanged/changed/removed；嵌入前先 `fetch_existing_vectors` 按 content_hash 取回旧向量，**只嵌 missing 的块**——改文档里一句话，其余块的向量全部复用。版本：`ENABLE_VERSIONING=true` 时同 source 多版本共存、`is_current` 标记最新，检索表达式强制 `is_current == true`，历史版本可查可按版本删。**真实事故**：`rebuild_collection()` 重建集合后没有清指纹库，导致后续所有上传**被静默跳过**（指纹说"没变"，但向量库已经空了）——修复是重建集合时连带清空指纹与 PG 派生表，并加了 `test_rebuild_clears_state.py` 回归。

### Q25 听说你把冷启动从 12.6s 优化到 1.8s？怎么做的？

**考察点**：依赖治理意识（这是 README 里的完整案例）。

**参考回答**：根因是一个**间接重依赖导入**：chunker 里 `from langchain_text_splitters import RecursiveCharacterTextSplitter`，它的 `__init__` 会导入全部 splitter 子类，连坐 `sentence_transformers → transformers → torch(+datasets, nltk)`——只为用一个切分器类，每次进程启动多付约 11 秒、5000 个模块，而且 Web 服务、A/B 子进程、切块 worker 全在白付。三项修复：① 自己写了**纯标准库的等价递归切分器**（`recursive_splitter.py`），切块结果逐字节一致——用 285 组真实语料 × 边界参数比对验证，并用 `sys.modules` 断言防回归（防止有人把 langchain 切分器写回热路径）；② 应用入口惰性化：chat 路由的 service 导入挪到请求时；③ 模型预热后台化：lifespan 里 `asyncio.create_task + to_thread` 加载嵌入/重排模型，端口绑定不被阻塞，就绪性由 `/api/health/ready` 门禁把守。结果：入口导入 12.6s→1.8s，切块模块 10.9s→0.4s，导入链路不再碰 torch。

### Q26 查询改写和分解具体怎么做？LLM 挂了怎么办？

**考察点**：Agentic 编排细节 + 降级路径。

**参考回答**：rewrite 节点复用 `rewrite_query`：轻量模型（qwen-turbo，降低改写延迟）输出 JSON——3-5 个关键词、1 条改写查询、3 个子查询；retrieve 节点对"改写查询 + 子查询"逐个检索（跨知识库），merge_docs 按 content 前 200 字符去重合并。**降级**：LLM 调用失败回退到纯规则——抽关键词、关键词两两组合生成子查询，保证链路不断。可选增强还有 HyDE（LLM 先生成假设性答案、用其向量扩召回，权重 0.5）。**召回深度是统一常量**：粗排恒为 50、精排恒为 5，与问题复杂度无关——行为可预测、便于评测对齐，也避免"同一问题在档位边缘漂移"的不确定性。这里我照样主动交代一个缺口：元数据过滤只在标准链路传入检索器，LangGraph 的 retrieve 节点没传 filters，是我记录在案的待修项。

## 四、极端场景下的异常处理

### Q27 断崖检测在什么极端情况下会出问题？怎么兜底？

**参考回答**：三种。① **全断崖**：排名第一远高于其余（查询非常具体、证据唯一），若没有下限会截到只剩 1 条——兜底 `min_topk=5`（且不低于 `rerank_top_n`）兜住，保证 LLM 至少有兜底上下文；② **无断崖**：分数平滑下降但整体都低（召回整体失败），断崖检测不会触发——这**不该**由它负责，该由拒答策略负责（全部来源 rerank < 0.3 → 拒答）；③ **分数尺度漂移**：换重排模型/换融合方式后分数分布变了，0.40 与 0.8 两个阈值可能失准（注意 RRF 模式下 0.8 本就不可达，只有 0.40 在起作用）——所以两个阈值都可配、可禁用，且换模型必须重跑 A/B 重新标定。要澄清的常见误解：断崖检测**只截断，不扩召回**——它截掉低分上下文让生成更干净，但召回不够时它无能为力。

### Q28 拒答策略误伤了正例怎么办？（你们真实发生过）

**参考回答**：发生过，基线报告 G4：一道跨报告正例 rr-multi-007，检索到 8 条来源，但全部 rerank 分低于 `REFUSAL_MIN_RERANK_SCORE=0.3`，被判"检索不足"拒绝回答——这也是引用可溯源率 0.9444 差 0.0056 没达标的唯一原因。我的分析：误拒与幻觉是一对权衡，阈值过松会放行幻觉，过紧会拒掉"相关但重排分数标定偏低"的案例；而且 bge-reranker 的分数没有概率含义，0.3 这个绝对阈值依赖模型标定。处置原则写在报告里：**不该在小样本上只压误拒**（会把拒答率搞崩），应该扩样后把误拒率和负样本拒答率放在同一张 A/B 里一起调，必要时对"来源数多但分数低"的场景单独放宽。另外我们区分了两条拒答路径：策略拒答（answer_rejected=true）和模型自己改口说"未提供"——后者在负样本上 2/2 都发生了，说明低温度 0.1 + 引用约束的 prompt 本身有拒答倾向。

### Q29 LLM 超时、限流、返回垃圾，各环节怎么降级？

**参考回答**：按环节列：① **查询改写**失败 → 回退规则关键词 + 两两组合子查询；② **HyDE** 失败 → 跳过该增强，用原查询检索；③ **反思节点**失败 → 视为"检索充分"直接进生成（round=99），不让反思循环卡死主链路；④ **生成**失败 → 返回友好中文报错，不把底层异常串给前端；⑤ **图片 caption** 失败重试 2 次后用"[图片] 第 N 页"占位，仍入索引；⑥ **元数据抽取**失败 → 留空 + needs_review，不阻断入库。设计原则：LLM 是增强项不是依赖项，**每个 LLM 调用点都必须有非 LLM 的退化路径**，主链路（检索→生成）不允许被增强环节阻塞。另外所有 LLM 相关异常统一分类到 `exceptions.py` 的友好文案体系，SSE 流式路径用 error 事件下发。

---

### Q30 Milvus 或 PostgreSQL 挂了，检索链路什么表现？

**参考回答**：① **Milvus 连接/查询失败**：抛 `VectorStoreError`，并和"知识库无内容"**严格区分**——前者提示"向量库连接失败请稍后重试"，后者才是"未检索到相关内容"，因为两者的用户动作完全不同（等待 vs 换问法）；查询带 MILVUS_TIMEOUT_SECONDS 超时，不会挂死请求。② **重排模型加载/推理失败**：捕获后回退到 Milvus 原始排序并打 warning，检索链路保持可用——重排是增强不是依赖。③ **PG 不可用**：父块还原失败时**回退为子块内容**（宁可给小上下文不给空），整表存储不可用时表格退化为索引摘要，都只告警不抛错。原则还是那句话：基础设施故障降级服务，不放大成用户可见的 500。

### Q31 元数据抽错导致"静默漏召"，这类问题怎么系统性防御？

**参考回答**：这是我最花心思的一类问题，因为它的表现为"查不到"但根因在数据。四道防线：① **入库侧词表硬校验**（Q20）：非法值丢弃 + needs_review，杜绝自由文本进标量列；② **查询侧白名单 + 值校验**：`_normalize_metadata_filters` 只放行白名单字段，security_code 校验 6 位数字（能挡掉注入式的垃圾值），industry 校验申万词表；③ **多标的整条丢弃**：问题里出现多只不同股票时丢弃 security_code 条件——部分过滤比不过滤更危险；④ **人工兜底**：needs_review 的文档在前端标"待确认"，PATCH 接口只改 Milvus 标量、**不重新嵌入**（复用 fetch_existing_vectors 读回向量列），修正成本极低。还有一条产品化防线：自动推断的过滤条件在前端是**可见可改的 chip**，且专门加了 `infer_filters` 开关——没有它前端"清除过滤"只是清了本地状态，后端会把条件再推断回来，清除是装饰性的（这是实测发现的）。

### Q32 队列打满、服务关闭时，在途文档怎么办？

**参考回答**：优雅停机路径：关闭时**先排空在途文档**（drain），再释放进程池/线程池——不会把半入库的文档留在中间态。运行中打满：上传返回 503 + 客户端退避重试 + 指纹幂等保证重试不重复入库；同时 `queue_rejected_total` 指标会暴露背压频率，运维侧可以据此扩容或提醒用户错峰。单文件失败：task 置 failed 并给中文原因（比如"解析失败：MinerU 无法识别该文件"），同批其它文件不受影响。我还专门处理过测试环境的一个坑：conftest 里默认关闭 `ENABLE_METADATA_LLM`，否则单测会打真实 LLM API——单测耗时从 16s 涨到 36s 还打挂了时间敏感用例，这个教训是"**任何默认开启的外部调用都要有测试开关**"。

### Q33 乱码 PDF、扫描件这类"解析不了"的语料怎么处理？

**参考回答**：分层处理。① 文本层乱码：MinerU 内置 OCR 通路，我们语料里就有一篇，实测走 OCR 恢复；② 解析失败：抛 MinerUParseError，task 标 failed + 中文原因，**不重试轰炸**，临时目录默认清理（可配保留产物排障）；③ 半失败：页码匹配不上记 0 不猜、content_list 缺失降级为 pymupdf 文本块、再不行记 "none"——每一级降级都有日志；④ 上传前置校验：非支持格式、超大小直接 4xx。还有一个容易忽略的边界：`.md/.txt` 走**短路直读**不进 MinerU，纯文本不需要版式解析，白付模型成本。

### Q34 评测时遇到"A/B 不显著"怎么下结论？

**参考回答**：我的框架是三层判定：improvement / regression / **inconclusive**，配置信区间——配对 Bootstrap 10000 次、95% CI，主指标 CI 不跨 0 且护栏不回退才判 pass。18 篇基线上三组 A/B（hybrid_vs_dense、rerank_on_off、cliff_on_off）**全部判 inconclusive**，报告里如实写"20 题规模下置信区间跨 0，不足以定论"。这比硬编一个结论有价值得多：inconclusive 的正确动作是**扩样**或**换更强的信号**（比如把指标从聚合命中率换成 evidence_rank 分布），而不是反复跑直到显著——那是 p-hacking。同样的纪律还体现在：L0/L1/L2 聚合指标逐位相同，我没有下"BM25 无效"的结论，因为逐题看 7/18 是不同的，纯小样本巧合，还找了反例（数字型查询"153.62亿"混合检索把证据排到第 1）。

## 五、量化指标的评测方法

### Q35 评测集是怎么构建的？为什么强调"引文唯一命中"？

**考察点**：gold set 的可信度设计（这是本项目评测方法论的亮点）。

**参考回答**：三层结构。① **题面人工写**：`research_report_questions.json` 里每题有 query、参考答案、required_facts、quote_hint（引文提示词）；② **证据脚本定位**：`build_gold_set.py` 把 quote_hint 在 Milvus 全量块内容里做子串定位，**要求全库唯一命中**，命中 0 条或 ≥2 条直接丢弃该题——绝不手写 chunk id，手写极易打错一位，evidence_hit 就假性归零，整个评测白跑；③ **全量复核**：`check_hints.py` 用完整块内容再复核一遍唯一性——初版 `dump_chunks.py` 只导出 300 字符，看着唯一的引文可能在别的块正文深处也出现，实际抓到 4 条重复。最终 32 条候选引文 32/32 唯一，按配额选 20 题：**8 单跳定位 + 10 跨报告同主题整合 + 2 负样本**，29 条证据覆盖 15/18 篇，multi_hop 题强制证据来自 ≥2 篇不同文档，全部 review_status=approved。后来又扩了 interview30：保留 20 道 gold 原题 + 新增 10 道**模糊问法题**（去掉券商名/简称/报告期，证据与配对题相同），专门测"模糊表述"场景。

**追问预警**：为什么不用 LLM 自动生成？→ 试过：320 题规模上 LLM 生成器跑了 60 分钟基本卡在网络且质量不可控，自动生成的多跳题经常把两篇无关文档硬配对，`multi_hop_hit=0` 不能归因于检索（报告会单列 suspect_annotations）。离线脚本构建在本项目里**更强而不只是更省**：唯一命中约束保证了证据标注的绝对可信。

### Q36 具体指标的口径是什么？Recall@5 和 Ragas 的指标什么关系？

**参考回答**：检索层全部基于 **chunk id 精确匹配**：hit = 检索返回的 chunk id 与标注证据 id 字符串相等。Recall@5 = top-5 去重命中证据数 / 该题证据总数；Precision@5 = 命中数 / 固定分母 5；MRR = 1/首个命中位次（未命中 0）；evidence_rank 记录证据块排名（未命中记 k+1）；文档级另有 hit_rate@5（至少命中一篇相关文档）、MRR@5、NDCG@5、doc_coverage（多跳取 0/0.5/1.0）。还有两个自建指标：**parent_restore_rate**——子块进 top-5 后父块是否被正确还原（父块 50–3000 字符且引文是其子串才算 restored），专门监控父子链路；**negative_rejection**——负样本是否被拒答（关键词代理判定，原始答案落盘供人工复核）。Ragas 层是**四指标**：检索链路的 context_precision / context_recall，生成链路的 faithfulness / answer_relevancy（历史报告里还有 answer_correctness、context_entity_recall，后来按"四指标覆盖两条链路"的口径下线，避免一份报告读两套标准）。两层的关系：chunk-id 层是**地面真值**，Ragas 层是生成质量，生成侧 A/B 也把 recall@5 / mrr 当护栏；报告里明确写了坑——`context_recall` 的 LLM judge 普遍饱和给 1.0，多跳能力要看 doc_coverage / evidence_coverage / evidence_rank，不能看 hit_rate。

### Q37 "分层评测"的"层"是什么意思？L0–L5 怎么定义的？

**参考回答**：两层含义。第一层是**检索策略层**：L0 纯稠密（基线）→ L1 +BM25 混合（RRF）→ L2 混合不重排（与 L3 对照隔离重排变量）→ L3 +BGE 重排 → L5 L3+断崖检测（生产口径）；L4 永久空缺（占位号，历史上曾是别的配置）。跑全矩阵就能**逐层归因**：L0→L1 看混合检索增益、L2→L3 看重排增益、L3→L5 看断崖检测影响。第二层是**题型分层**：single_hop / multi_hop（跨文档）/ negative（负样本）/ vague（模糊问法），报告按题型分层汇总且**必须带样本数 n**。要纠正一个常见误解：L0–L5 是策略难度不是题目难度，题目难度另有 easy/medium/hard 字段。这个设计让我能说出"重排有效、召回不足"这种归因结论而不是一个笼统的"效果不错"。

### Q38 A/B 实验怎么保证可信？讲讲你的实验方法论。

**参考回答**：五条纪律。① **单变量**：每个实验一对臂，臂差异只用环境变量/strategy 覆盖表达（ab_rag.py --experiment rerank_on_off），杜绝"顺手改了别的东西"；② **执行顺序随机化**：双臂执行顺序按 seed 随机，降低顺序偏差（服务预热、缓存效应）；③ **抽样可复现**：按 question_type 分层抽样、seed 固定（默认 7）；④ **配对统计**：按 case_id 逐题配对，Bootstrap 10000 次、95% 百分位 CI，主指标 CI 不跨 0 且**护栏指标**（如 rerank 主指标 MRR、护栏 Recall/Precision）不回退才判 pass；⑤ **结果落盘可复核**：每次运行落 run_config.json / records.jsonl / per_query.csv（逐题明细含检索到的实际 chunk id 与 evidence_rank）/ report.md，任何数字都能回到原始记录。判定三态：pass / fail / **inconclusive**，inconclusive 不硬下结论。

### Q39 简历上"Recall@5 提升至 90%、MRR@5 提升至 1.0、上下文精确率提升 14.1%"——这些数字怎么来的？什么口径？

**考察点**：数字的真实口径。**这是全场最危险的问题，口径必须主动说清。**

**参考回答**（诚实版，建议主动讲口径）：
- **Recall@5 → 90%+**：来自旧迁移评测集（28 题）上**重排开关 A/B**：R@5 0.7143 → 0.9107（91.07%），MRR 0.5845 → 0.9071；配对 Bootstrap 判 pass（R@5 +0.1964，CI [0.054, 0.357]；MRR +0.3256，CI [0.199, 0.456]）。口径是"混合检索基础上开/关 BGE 重排"的增量，不是端到端从零到 90%。
- **MRR@5 → 1.0**：来自早期 n=5 的 langgraph_on_off A/B，**文档级** MRR@5 从 0.9 → 1.0（Agentic 臂）；正式协议下 MRR 最高 0.9071，从未到 1.0。
- **上下文精确率 +14.1%**：历史 n=5 的 langgraph_on_off 报告记录 context_precision 0.6650 → 0.7589（相对 +14.12%），同表 faithfulness -10%、composite -0.96%。这只是旧协议下的五题观察，**不能作为 agentic-v2 的提升证据，也没有据此证明统计显著提升**；历史产物保留原样。
- **"100 题分层评测集"**：撤回这一已完成声明。`scripts/results/agentic-v2/manifest.json` 只读枚举现有 JSONL 与旧 Markdown：评测资料有 146 条原始记录，按规范化问题与事实标注精确去重并归并显式配对后为 **94 个潜在独立组**；其中 70 条记录存在近重复、同 ID 标注冲突等待复核项，满足当前已审 Gold 条件的独立组只有 **12 个**。另有 6 条 judge 锚点、4 条回归用例，单独统计。94 仍是待审核的清单数，不能说成 94 个已确认独立样本，更不能把集合条数直接相加称作 100 题。当前没有 100 个独立已审样本，也没有 agentic-v2 的正式提升结果。

**我会这样收尾**：这些数字我都能给出处和口径，但我也想主动说明它们的局限——样本量小（n=5 或 28 题）、部分来自旧语料；在当前 18 篇研报正式协议下，Recall@5 基线只有 0.27–0.30，主要瓶颈是一阶段召回（证据进 top-20 仅 31%），这也是我在报告里明确列的差距清单和改进方向。我认为能把数字讲清楚、并说清它不适用范围的候选人，比只会报漂亮数字的可信。

**追问预警**：为什么正式协议下只有 0.27？→ 三个原因：语料从泛金融文档换成"全库没有任何同标的"的 18 篇研报，块级精确命中的难度完全不同；**那次测量跑在 bge-small-zh 512 维索引上**（弱于设计文档的 bge-large，report.txt G3；09-30 已换 bge-m3 1024 维并重灌，但基线待复测）；模板块（免责声明/资料来源）挤占 top-5 槽位 15–31%。改进清单已列：在新索引上复测基线、压块进 512 token 窗口后重灌向量、block_type 降权、把元数据过滤接进 Agentic 链路、语料扩量后复测。

### Q40 你们怎么定位"瓶颈在召回不在重排"的？这个过程讲一下。

**考察点**：数据驱动的归因能力（报告第 4 节 G1/G6 的推理链）。

**参考回答**：三条证据。① **候选池 vs top-5 命中率相等**：L3/L5 层上，证据进入 top-20 候选池的比例和最终进 top-5 的比例完全相等（都约 27.6%/31%）——说明重排**没有浪费任何已召回的候选**，转化率 89%，瓶颈在上游；② **模板块挤占**：top-5 槽位里免责声明/资料来源/图片块占 15.3%–31.1%，且文档级命中 82.8%–94.4% 而精确块命中只有 27.6%——"检索到了正确文档，却选中了同一篇的错误块"；③ **重排 A/B 显著为正**：28 题迁移集上重排是唯一判 pass 的实验（CI 不跨 0）。所以结论是"一阶段召回是主瓶颈、重排勿重复改造"（G6 明确写了"不应把预算花在重排参数上"）。这种"先分离变量、再归因"的做法正是 L0–L5 分层矩阵的价值。

### Q41 拒答判定的口径出过什么问题？怎么修正的？

**参考回答**：出过一个典型的**评测口径 bug**：首轮统计负样本拒答正确率算成 1/2 = 0.5，排查后发现不是模型答错，而是**判定关键词表漏了"未提供"这类常见拒答措辞**。修正动作：把 runner.py 和 ab_runner.py 里两份重复的关键词表合并为一份并补全，新增单测锁定；用 `--reuse` 复用已落盘的原始答案复评（不重复消耗 LLM 调用），复评 2/2。顺带发现关键词代理**不能用于正例**——一个 266 字、带 5 条引用的正常作答被误判成拒答，所以正例只看生产策略标志 `answer_rejected`。这个案例的教训我总结成一句话：**评测代码和生产代码一样需要测试**，判定逻辑的 bug 会把"系统错了"误报成"系统对了"或反之。

### Q42 Ragas 或 LLM judge 指标哪些坑你们踩过？

**参考回答**：三个，都写进了 README 的"指标口径与坑"。① **hit_rate 在多跳上饱和**：命中 2 篇相关文档中任意 1 篇就是 1.0，无法反映覆盖度——所以多跳要看 doc_coverage（0/0.5/1.0）和 evidence_coverage；② **context_recall 的 LLM judge 普遍给 1.0**：对 top-5 上下文几乎不区分——检索能力评估不依赖它；③ **自动生成多跳题的证据不可信**：LLM 把随机抽的两篇文档硬配对出题，第二篇常常与问题无关，此时 multi_hop_hit=0 不是检索的错——报告单列 suspect_annotations 清单，排查顺序固定为：先看坏标注占比 → 再看 evidence_rank 是否落在 top-15 候选内却被重排截断（那才是重排问题）→ 最后才动检索参数。另外成本上我们也量化了：生成侧每题每臂 4 次 judge 调用（RAGAS 四指标）+ 改写/HyDE/生成，这是我们把大批量评估改用 chunk-id 客观指标、Ragas 只跑小样本 A/B 的原因。

### Q43 RAGAS 四指标怎么映射 RAG 的两条链路？定位问题时怎么用？

**考察点**：指标不是越多越好，要能一对一回溯到链路环节。

**参考回答**：四指标**恰好覆盖两条链路各两项**。检索链路：`context_precision` 度量检索噪音（10 个 chunk 只有 2 个有用 → 精确率低），`context_recall` 度量知识盲区（关键信息压根没召回）。生成链路：`faithfulness` 防幻觉（陈述能被 Context 支撑的比例），`answer_relevancy` 防跑偏（让 LLM 反向生成问题，再和原问题做向量相似度）。定位问题时按链路拆解：`context_recall` 低 → 查检索策略；`context_precision` 低 → 查噪音/切块；`faithfulness` 低 → 生成幻觉；`answer_relevancy` 低 → 答非所问。

两个工程细节。① **四指标不单独成立，要和 chunk-id 客观层交叉看**：`context_recall` 的 judge 对 top-5 普遍饱和给 1.0，所以报告里它旁边永远并排着按证据 id 精确匹配的 Recall@5 / Precision@5 / MRR；生成侧 A/B 也把 `recall@5`、`mrr` 当护栏——**生成质量不能靠牺牲检索能力换**。② **口径收敛**：早期还跑 answer_correctness 和 context_entity_recall（fast/full 两档），后来下线为固定四项，因为四指标之外的口径会让同一份报告读两套标准，而且这两项与四项高度共线。

**追问预警**：为什么不留 answer_correctness？→ 它和 faithfulness + context_recall 的组合信息高度重叠，且带 reference 的语义相似度对小样本更抖；真要评"答得对不对"，我用证据级 Recall@5/MRR + 人工抽检，比再加一个 judge 指标更可信。

### Q44 LLM-as-Judge 的三个典型偏差，你们怎么防？

**考察点**：知道 judge 有偏差只算常识，能给出**可观测指标 + 可执行开关**才算工程。

**参考回答**：三类偏差各有一套机制和一个可观测指标。① **位置偏差**（裁判偏爱先出现或后出现的候选）：成对裁判同题评两次（A 在前 / B 在前），呈现顺序由 `Random(f"{seed}:{case_id}")` 决定，两次一致才采纳、冲突判 tie 并记 `order_flip`——**换序翻转率本身就是位置偏差的量化值**，另有"先出现者获胜率"和呈现顺序平衡做审计。② **长度偏差**（倾向给长回答高分）：裁判 Prompt 里明确"简洁准确优于详细冗长、不因条目多而加分"；`per_query.csv` 记录 `answer_chars`，报告给每臂字数与"分数~长度"的 Spearman；更关键的是**长度匹配对照**——只在两臂字数比 ≤1.25 的配对上重算 Δ，若原始 Δ 与匹配后 Δ 方向相反就打 `sign_flip` 告警，说明结论很可能是长度混杂。③ **自我强化偏差**（生成模型和裁判同族时给自己加分）：我们生成和主裁判都是 DeepSeek，属于典型的自评场景，所以报告恒标 `self_judged=true`；解决方案是引入**第二模型族**（默认 qwen-turbo）在同一批 case_id 上重跑四指标，给出偏置、Spearman 和"A/B 方向是否一致"。第二裁判不可用时报告写 `self_preference_unverified`，**不编结论**。

**追问预警**：这些开关默认都开吗？→ 不是，按成本分层。长度遥测和说明恒开（零额外调用）；锚点样本默认开（约 6 条）；成对裁判 `--pairwise N` 默认关（换序两次 = 2N 次调用）；跨模型校验 `--cross-check N` 默认关。默认关的项在报告里写"未运行"，不会被误读成"通过了"。

### Q45 judge 的尺度会不会漂移？怎么和人类判断对齐？

**考察点**：有没有把"评测系统"本身当成需要校准的东西。

**参考回答**：两条工程校准策略。① **锚点样本**：我维护了一组人工构造、期望分数区间已知的黄金用例（比如"有据的短回答 faithfulness ≥ 0.9"、"上下文没有支撑的数字 faithfulness ≤ 0.3"、"5 条上下文只 1 条相关 context_precision ≤ 0.4"），每批评估**独立跑一次**（不混进题目均值），逐项检查实测值是否落在区间内，输出通过率与平均越界幅度。默认只报告，`--anchor-strict` 才在越界时判本次实验失败——因为期望值是人写的、judge 本身有抖动，默认硬门禁会制造假失败。② **人工标注对齐**：每周抽 50–100 条人工按同一套 0~1 口径打分，计算每个指标的 MAE、偏置（人-机）、Spearman 与"≤0.2 一致率"，并给 `recommended_offset`（judge 分加上它就对齐人类均值）。判定分三档：偏置 ≤0.1 且 Spearman ≥0.5 算 `aligned`；偏置 >0.2 或 Spearman <0.2 算 `divergent`（judge 尺度不能信）；其余算 `offset`（可校准）。

一个容易被忽略的实现点：**标注和评估必须解耦**。抽样导出只读已落盘的运行产物、不花 LLM 成本，所以历史运行也能补做校准；早期产物没有 `case_id` 字段，我们就用"臂名 + 问题原文"生成稳定键，避免校准只对新报告可用。

### Q46 如果给你两个月继续优化，你的路线图是什么？

**参考回答**：按基线差距清单的优先级。① **G1 一阶段召回**（最高优先级）：在新索引（bge-m3 1024 维）上复测基线——旧基线跑的是 bge-small 512 维（report.txt G3），换模型后指标尚未复测；子块预算已对齐 embedder 窗口并把上限压到检索单元尺度（×4 → ×1.4、256 token = 358 字符，实测 0% 超窗 / 稠密覆盖 100%、39% 的父块被真正切开），但**索引仍停在旧切块上**：需要重建 gold 证据 id（子块 id 是内容哈希，切块一改全部失效）+ 全量重灌（重建集合，成本可控）；核查查询改写/HyDE 的实际生效性（生产链路含改写但 doc 级命中与块级命中的落差说明增强可能没起作用）；② **G2 噪声挤占**：入库侧过滤或降权模板块（免责声明/资料来源），按 block_type 加权、图片块默认降权——文档级命中 94% 说明信息在库里，是"选错块"；③ **把元数据过滤接进 LangGraph retrieve 节点**，让"查某只票/某行业"走结构化过滤而不是全库语义；④ **扩样复测**：语料到 50+ 篇后重跑基线与全部 A/B，把 inconclusive 的三组实验补出显著性；⑤ 调拒答阈值时把误拒率和负样本拒答率作为**联合目标**，避免单边优化。每一步都先 A/B 后上线，无显著提升就回滚——这是我在这个项目里养成的纪律。

## 六、场景驱动工程拆解：四类真实研报问题，今天会怎么翻车、怎么修

> 前五节讲"系统是什么"，这一节讲"分析师真问起来会发生什么"。每类按 **现状翻车点（对着代码推演）→ 技术方案（最小改动优先）→ 评测怎么补** 展开。面试里最狠的追问就是拿一道真实问题问"你这系统能答吗"——正确姿势是能/不能 + 卡在哪一行代码 + 怎么补。

### 6.1 精确数值型："宁德时代 2025 年归母净利润预测是多少？哪家券商给的？"

**现状翻车点**：

1. **表格行不在索引里**。财务表的索引子块只有"表头 + 首行"（`_table_summary`），"2025E 归母净利润"这一格在第 3、4 行——稠密和 BM25 都摸不到。能否答对全赌两件事：表头恰好含"归母净利润"把整表带进 top-5，且 `_truncate_table` 的 8000 字符**按行序截断**没把这行切掉（截断不感知查询要哪行）。
2. **单位口径陷阱**。表格原文常是"归母净利润（百万元）51,234"，分析师问"多少亿"。让 LLM 现场换算是在赌算术——错一个量级就是最恶劣的幻觉（数字专业、结论全错）。而 spec 明确"不做口径归一化"，必须回到原文口径。
3. **"哪家券商给的"接不上**。broker 在 chunk 标量里有，但 `build_context` 块头只注入报告日期/页码，prompt 也没要求标注券商——答案经常漏归属。
4. **数字幻觉没有出口检查**。CitationValidator 只校验"引用挂得对不对"（语义相似度），**不校验数字本身**——512.3 亿写成 521.3 亿照样满分通过。

**技术方案（按性价比）**：

- **S1 表格行级索引**（改动小、收益最大）：入库时对财务表逐行生成子块——"表头 + 该行"一个 child，parent_id 指向整表。98 张表 × ~20 行 ≈ 2000 个新子块，成本可忽略；row chunk_key = sha256(parent_id:row_hash) 保持增量幂等。"2026 年 EPS 用哪版预测"直接命中那一行，整表展开复用不动。
- **S2 数值出口校验（数值版防幻觉）**：答案落盘前正则抽出全部数字（千分位/全角归一），逐个回查"是否逐字出现在其引用的来源 content 里"（原文口径原样比对，不做换算校验）；查不到 → 标 low_confidence 或改写为"原文为 X（表 N）"。纯规则、零 LLM 成本，对数值幻觉近乎精确打击。
- **S3 块头注入券商**：块头模板从"日期/页码"扩成"券商/日期/页码" + prompt 契约"数值结论必须写明券商与口径"。一行改动。
- **S4 截断升级为"按相关性保行"**：截断前按查询关键词对行打分，8000 预算内保高分行，sources 标"保留 M/N 行（按相关性）"。

### 6.2 跨文档对比型："中金和中信对同一只票的评级差异在哪？目标价差多少？"

**现状翻车点**：

1. **评级/目标价根本没抽**——spec 的明确非目标（评级格式不统一、抽错风险高）。所以这道题今天**答不了**：检索只能碰运气捞到正文提评级与否的段落，无法结构化对比。面试必须直说，再给补法。
2. **多实体路由卡在两处**。"中金和中信"是 `broker in [中金, 中信]` 能表达的，但"同一只票"是口语指代，security_code 得从对话历史解析；且 LangGraph 的 retrieve 节点**没传 filters**（已知缺口），过滤只在标准链路生效。
3. **"对比"需要两个来源同时在上下文里**。重排 top-3 很可能只进了中信那篇，中金被断崖截掉——"对比"退化成"单边陈述"。
4. **"过去 30 天哪些券商上调了白酒行业评级"是聚合题不是检索题**。"哪些/几家/排名"要全量扫描 + 集合运算，top-k 向量检索在范式上就不匹配；且"白酒"不是申万一级（是食品饮料下的二级），查询侧词表校验会把 industry 条件丢弃 → 退化全库扫描。

**技术方案**：

- **S1 评级/目标价结构化抽取**（重启非目标，但带安全阀）：正则优先（评级词表 + "目标价 XX.XX 元"模式，研报首页格式相对固定）→ LLM 补抽 → `needs_review` 人工确认；存 Milvus 标量 + PG `rating_history(broker, security_code, rating, target_price, date)`。守住原 spec 原则的办法：**输出永远"原文口径 + 出处"**，"推荐"≠"买入"不做语义映射，对比只并列呈现、不做裁决。注意加标量字段要重建集合——和重灌向量一次做掉。
- **S2 意图路由 + 结构化查询工具**：LangGraph 加路由节点（规则起步："哪些/几家/对比" → 结构化；"多少/什么值" → 表格通道；其余 → 向量）。聚合题路由到 SQL/lookup 工具查 rating_history（行业/日期过滤 + 按股票分组取最新 vs 前值 → diff 出"上调"）。这是对 Agentic RAG 的诚实注解：**向量管语义，结构化工具管聚合**，硬用向量做聚合是范式错误。
- **S3 对比题的上下文配额**：意图为对比时，重排后按实体（broker/股票）分组配额，保证每个实体至少一条来源进上下文，答案要求逐实体分段引用。
- **S4 查询侧行业层级归一**："白酒 → food_l1=食品饮料 + l2=白酒"做查询侧映射表（入库侧已有 l2∈l1 校验，查询侧补齐），防止词表校验误杀有效条件。

### 6.3 逻辑链追溯型："这个目标价是怎么推导出来的？用了什么估值方法和关键假设？"

**现状翻车点**：

1. **推导链横跨同一篇的多个章节**（目标价在摘要、估值方法在中段、假设在附注），而检索是块级的：top-3 重排 + 每块 2000 字符预算，很难同时装下三段。文档级命中 94.4% 但块级命中仅 27.6% 的老问题，在这类题上最致命。
2. **敏感性分析是算术题**："碳酸锂再跌 10%，盈利影响多大？"——研报有敏感性表就该引用原表；没有的话，LLM 自己外推弹性 = 编造定量结论，而且带着数学的外形，比普通幻觉更危险。

**技术方案**：

- **S1 同文档邻域扩展**：命中 top-1 后按 heading_path 拉同文档兄弟块（同章节/相邻章节）进候选池，交给重排统一裁决。这同时是 G2（文档对了、块选错了）的通用修法。
- **S2 目录工具（Agentic 的正当场景）**：入库时存每篇 heading_path 树，Agent 加"查目录"工具：先定位"估值方法/关键假设/敏感性分析"章节，再按 source + heading_path 精确取块。追溯题从"祈祷检索"变成"按图索骥"。
- **S3 敏感性问题的降级语义**：先检索"敏感性/情景假设"关键词 + 表格通道；命中 → 引用原表；未命中 → 明确答"该研报未提供此敏感性分析，原文假设为 X [N]，无法可靠外推"。原则：**定量结论必须可溯源，LLM 只搬运标注、不做心算**。

### 6.4 时间/版本敏感型："这是最新版吗？和上个月那版相比，调整了哪些假设？"

**现状翻车点**：

1. **"版本"在研报语料上是个陷阱概念**。`ENABLE_VERSIONING` 是为"同一文件重传修订"设计的（is_current/按版本删）；但研报的真实版本形态是**同券商同标的不同日期的新 PDF**——文件名不同、走不同 source，文件版本机制罩不住。今天答"这是最新版吗"只能靠检索碰运气，完全可能把三个月前的旧块检索出来还言之凿凿。
2. **跨文档 diff 没有现成链路**。"和上个月那版相比改了哪些假设"需要：按 (broker, security_code) 找上一篇 → 内容级 diff → diff 落到章节。原料其实都有（content_hash / diff_chunks / SimHash），但没有对外的"两文档对比"路径。
3. **相对时间没有锚**。"过去 30 天"需要"今天"：infer 过滤的 prompt 若未注入当前日期，LLM 只能猜区间（这点面试前值得实测确认）；即便注入，也要在解析层把相对时间落成绝对区间。
4. **"财报发布后哪些研报还没更新"又是聚合题**：需要财报披露日历 + 每只票最新研报日期 + 集合差——不是 top-k 检索能答的。

**技术方案**：

- **S1 把"版本"定义为元数据时间序列**：按 (broker, security_code, report_type) 分组、按 date 排序，latest=最新；"是否最新"走元数据查询而非向量检索（顺带规避旧块被检出的陷阱）。文件级版本机制保留给"同一文件修订重传"的真实场景。
- **S2 跨文档 diff 复用增量设施**：两篇 PDF 的 chunk manifest 按 content_hash 对齐 → changed/removed → 映射回 heading_path，直接产出"调整集中在盈利预测假设章节，共 N 处"的答案骨架，changed 块本身就是引用来源。增量机制反向用一次，边际成本低。
- **S3 相对时间解析**：infer prompt 注入当前日期，"过去 30 天/最近一周"在 infer 阶段落成 date gte/lte 绝对区间（现有 date 过滤通道直接消费）。
- **S4 新鲜度一等公民**：不设默认时间窗的决策不变（不静默丢旧报告），但答案层加新鲜度提示——同标的存在更新报告而命中了旧报告时，显式标注"该标的存在 2026-09 版本，本答案基于 2026-06 报告"。"财报后哪些没更新"走 S2 的结构化通道查集合差。

### 6.5 收束：改造优先级表（面试可直接引用）

| 改造 | 服务的问题类型 | 成本 | 预期收益 |
| --- | --- | --- | --- |
| 表格行级索引 | 数值 | 小（入库侧） | 数值题从"赌"变"保证" |
| 数值出口校验（纯规则） | 数值/全部 | 小 | 数值幻觉近乎清零，可做护栏指标 |
| 块头注入 broker + prompt 契约 | 数值/对比 | 极小 | 归属不再漏 |
| 相对时间注入当前日期 | 时序 | 极小 | "过去 30 天"可解析 |
| LangGraph 接入 filters（已知 TODO） | 对比/时序 | 小 | 补上 Agentic 链路结构化能力 |
| 同文档邻域扩展 / 目录工具 | 追溯（兼修 G2） | 中 | "文档对块错"的通用解 |
| 意图路由 + 结构化查询工具 | 对比/时序聚合 | 中 | 聚合题从"不可答"变"可答" |
| 评级/目标价抽取（needs_review 安全阀） | 对比 | 中 | 重启非目标且守住"原文口径" |
| 跨文档 diff（复用 content_hash） | 时序 | 中 | "改了哪些假设"可答 |

**评测怎么补**：四类问题各进分层评测集（沿用 interview30 的 gold+变体做法），新增三个块级指标——**numeric_exact**（答案数值与来源逐字一致率）、**pair_coverage**（对比题两来源同时进上下文比例）、**diff_recall**（版本 diff 检出 changed 块的召回率）。没有这三个指标，"支持数值问答/对比/版本对比"就又是一句不可验证的话。

### 6.6 实测复盘：重灌后 gold20 暴露的三个失败模式与修复（2026-10-01，全部可验证）

**背景**：切到 bge-m3、子块上限 256 token（358 字符）并重灌（实测 1504 块 = 1080 text + 98 table + 326 image）、重建 gold 后复跑 L5：Recall@5 = 0.2407（单跳 0.375 / 多跳 0.133）。逐题复盘出三个失败模式，其中两个查询侧修复当天落地并复测，第三个待重嵌验证。

**失败模式 1：短标题块进不了候选池，或进了被重排挤掉**（9/29 条证据 ≤120 字）

- 机制：15 字的证据块（如「## 加速赋能 AI 新药研发」）正文里**没有**公司名/券商名——查询词与块文本零交集，BM25 词频为 0、稠密对不齐；而重排输入就是裸 content（`pairs=[[query, content[:2000]]]`）。**块外信息（security_name/heading_path）就躺在 Milvus 标量字段里，但从不参与打分**。
- 修复 A（查询侧，已落地）：重排候选文本注入上下文——`security_name + heading_path + content`；**刻意排除 broker/title**（元数据抽取质量不可靠：实测出现 'kysec' 拼音、张冠李戴的券商名），错误上下文会让 cross-encoder 主动压低正确块。
- 修复 B（嵌入侧，代码已落地、待强制重嵌生效）：嵌入输入做同样注入。已有向量按 content_hash 复用不会自动重算，需要 rebuild_collection 强制一次。

**失败模式 2：表格霸占 top-5**（90 个槽位里 22 个是表格，23%）

- 机制：表格索引文本是"表头 + 行标签"，公司名/科目名关键词密度天然高；正文块变小（358 字符）后，表格的关键词密度相对优势被放大。
- 修复 D1（已落地）：重排后最终选取加**非文本块配额** `RERANK_MAX_NON_TEXT_BLOCKS=2`，配额耗尽按重排顺位回填（宁可有偏不缺条）。
- 实测：22/90 → **9/90（10%）**。

**失败模式 3：多跳 10 题零全中**（均值 0.133）

- 先排除结构性借口：多跳题每题只有 2~3 条证据，**top-5 物理装得下**——不是口径问题，是排序分散度问题：单文档霸榜把第二篇文档的证据挤掉。
- 修复 D2（已落地）：**每文档配额** `RERANK_MAX_PER_SOURCE=2`（6.2-S3"对比题按实体配额"的通用版，per-source 比按实体更弱但零意图识别成本）。
- 实测：分散度约束生效，但多跳 Recall@5 不变——缺的第二篇证据**本来就不在候选池里**，回到模式 1 的嵌入侧。

**A+D 当日复测（查询侧，旧向量）**：MRR 0.2407 → **0.3056**（+27%；单跳 MRR 0.229 → 0.375），Recall@5 不变，表格槽位 22 → 9。解读：**排序质量上去了，召回集合没变**——恰好印证诊断：短标题块的问题在候选池入口（嵌入侧），不在排序；重嵌后复测是下一步，预期补回 Recall。

**面试话术**：三个模式一个共同根因——**打分输入 ≠ 块的完整信息**。重排模型没有错，它只能对送进来的文本排序。修法是让 security_name/heading_path 参与打分（content 不动 → 块 id 与 gold 证据引用不受影响）；配额是 MMR-lite：确定性规则、不引新模型、可回填、可一键关闭。
